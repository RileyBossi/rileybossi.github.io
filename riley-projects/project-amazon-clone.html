Why This Project

My programming background was primarily Java, Python, SQL, and Assembly Language with some HTML and CSS. I knew I needed to understand JavaScript — not just to code, but because JavaScript is the primary attack surface of the modern web. DOM-based XSS, prototype pollution, insecure deserialization, and client-side logic flaws all require deep JavaScript knowledge to both execute and defend against.

The best way to understand how something can be abused is to build it. Building a full e-commerce application from scratch exposed me to the exact patterns attackers look for: where input is accepted, where data is stored, and where trust decisions are made.

What I Built

  • Dynamic product catalog loaded from a JavaScript data structure, rendered to the DOM with event-driven programming
  • Real-time cart management — adding, updating, and removing items with live UI updates
  • Local storage implementation for cart persistence across page reloads
  • Multi-page checkout workflow with order processing and confirmation
  • Responsive design across all pages
  • Version control with Git throughout the project
  • Basic API integration

Security-Focused Observations

Client-Side Trust is Dangerous

Building the cart and checkout logic entirely in JavaScript made it immediately obvious how easily a user can manipulate prices, quantities, and product IDs directly in the browser console or through DevTools. Any server receiving this data without revalidating it server-side is wide open.

DOM-Based XSS Surface

Every time I rendered user-controlled data into the DOM (product names, quantities, form inputs), I was creating a potential XSS injection point. Implementing it without a framework like React meant there were no built-in escaping protections — you had to think about it explicitly every time.

Local Storage Risks

Storing cart data in localStorage was convenient, but it's accessible to any JavaScript running on the page. If the site were vulnerable to XSS, an attacker could read or manipulate stored cart state. Storing session tokens or sensitive data there would be even more dangerous.

Code Readability as an Attack Surface

Writing the application from scratch gave me a clear sense of how attackers reverse-engineer JavaScript. Variable names, function structures, API endpoint patterns, and business logic are all visible in client-side code. Obfuscation helps marginally but determined attackers can still map out the attack surface.

Key Takeaways

Never trust client-side input

Every input in this project was potentially attacker-controlled. The takeaway for defense: always validate and sanitize server-side, regardless of what client-side controls you've built.

JS builds security intuition

Understanding how JavaScript executes, how the DOM works, and how data flows through a web app makes reading vulnerability reports and pen test findings much more concrete.

The attack surface is everywhere

Price fields, quantity inputs, product IDs, URL parameters — every one of these is a potential injection point or business logic flaw waiting to be found.

Frontend and backend security are connected

Seeing how client-side logic makes API calls reinforced that web app security can't be thought of as frontend vs. backend — the entire request/response chain has to be considered together.
