The Problem I Had to Solve

Microsoft Sentinel was only available to me through my school's Azure tenant, where I had limited permissions. Full admin access to Microsoft Entra ID was only available in my personal test tenant. These two tenants couldn't be connected directly — so I had to engineer a solution that bridged them using Azure-native services.

This constraint turned out to be the most educational part of the project. Real enterprise environments are messy — data lives in different places, permissions are limited, and you have to work with what you have. Solving that puzzle with Logic Apps and blob storage gave me practical experience with cloud automation I wouldn't have gotten from a clean tutorial.

Identity Environment (Personal Entra Tenant)

Before worrying about Sentinel, I built a realistic identity environment to generate meaningful log data:

  • Created multiple test users with different roles: Global Reader, User Administrator
  • Organized users into security groups: Finance, IT, Sales, HR
  • Enabled per-user MFA and Conditional Access policy-based MFA
  • Created Conditional Access policies to enforce MFA from outside the US and block legacy authentication clients
  • Enabled Identity Protection risk policies (user risk and sign-in risk)
  • Simulated sign-ins, risky behavior, and policy triggers to generate audit and sign-in log activity

Log Ingestion Pipeline

With Sentinel unavailable in my personal tenant, I built a cross-tenant ingestion pipeline using blob storage as the bridge:

Entra Sign-in Logs
→
Export as .csv
→
Azure Blob Storage
→
Logic App (scheduled)
→
Log Analytics (EntraLog_CL)
→
Microsoft Sentinel

Step-by-step

  • Exported Entra sign-in logs as a CSV from the personal test tenant
  • Created an Azure Storage Account and private blob container in the school tenant
  • Uploaded the log file to blob storage
  • Deployed a Logic App with a scheduled trigger that reads and parses each row from the CSV
  • Configured the Logic App to send each log entry to a custom Log Analytics table (EntraLog_CL) linked to Microsoft Sentinel
  • Verified ingestion by querying EntraLog_CL in Sentinel's Log Analytics workspace with KQL

Key Takeaways

Constraints drive creativity

Not having a direct tenant connection forced me to learn Logic Apps, blob storage, and custom log tables — tools I wouldn't have touched in a simpler setup. The workaround became the most valuable part.

Conditional Access is powerful and nuanced

Building and testing CA policies myself — blocking legacy auth, requiring MFA from abroad — made the tradeoffs between security and usability concrete in a way reading documentation doesn't.

Custom log tables need careful schema design

Ingesting CSV data into a custom table required thinking carefully about field names, types, and how KQL would query them later. Garbage in, garbage out applies to SIEMs especially.

Identity logs are rich with signal

Entra sign-in logs include location, device, risk score, CA result, and more. Querying these with KQL to find anomalous sign-ins gave me a clear sense of why identity logs are so valuable to defenders.
